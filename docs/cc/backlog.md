This is composition, not privilege — a nested declaration still cannot introduce an issuer the measured trust root does not authorize, nor lower an SVN floor. Depth is capped at 4 as a cycle backstop, first declaration wins, and out-of-scope declarations are dropped with a logged reason rather than failing an already-committed delivery. C-ACI/hcsshim has the same capability via `candidate_fragments`, and puts the switch in the same place — `includes: ["fragments"]` on the *declaration* decides whether the fragment behind it may contribute further declarations — but that switch is a bare boolean: once set, the fragment may name any `(issuer, feed)` pair, and there is no depth cap or cycle guard. Unit-tested (6 new policy-crate tests) **and verified live 2026-08-04** on `coco-dev-2` by stage 07 cases `07f`-`07k`, which stage 06 feeds with three new signed fixtures (a child, a parent declaring it same-issuer, and a parent declaring a foreign issuer). The oracle is pod phase: a nested declaration marked `required: true` is an obligation the host never satisfies, so a registered declaration blocks `create_container` and a dropped one boots -- reading the scope decision in both directions from outside the guest. `07f` no grant -> runs (off by default); `07g` `same-issuer` -> blocked (registered); `07h` parent+child delivered -> runs (chain completes); `07i` `same-issuer` with a foreign nested issuer -> runs (dropped); `07j` explicit list naming that issuer -> blocked; `07k` `any-authorized` -> blocked. `07i` and `07j` deliver the same fragment and differ only in the grant, so neither can pass by delivery failure. **Namespace grants now come from measured state, not the fragment** (F-62): the SRM records what each `(issuer, feed)` may contribute, taken from the BL-8 declaration or the trust root, and the effective scope is that grant intersected with the fragment's own request, so neither side can widen the other. Previously the fragment's self-signed `includes` alone decided, which let any authorized issuer claim a namespace the base policy meant a different issuer to fill. A grant may also withhold the module entirely (`allow_module = false`), accepting a fragment for its SVN, receipt and ordering record while it contributes no rules — hcsshim's metadata-only load. **Receipt requirements are conjunctive** and gained hcsshim's grammar: `*` (any validated receipt), `TTL:<subject>` (validated by a key a named Trust List vouched for), or a ledger id. A list now means all-of rather than any-of, matching `fragment_receipts_ok`; single-entry lists, which is every existing configuration, are unaffected. Satisfying a conjunction needs several receipts, so `LoadPolicyFragmentRequest` carries `extra_receipts` (`<ledger>=<hex sig>`), each an additional Stage-1 countersignature over the same statement, each scoped by the same `allowed_ledgers`. **Fragments may be parameterised** (F-64): a fragment reads values via `parameter("name")` rather than hard-coding them, so one signed artefact serves several deployments without a re-sign per value. Values come from the declaration (base policy or trust root), never the fragment or the host, and are bound after signature verification by appending a constant and a total resolver (supplied → the fragment's own declared default → null) to the module. One set per declaration, where hcsshim tries every set because its loading is lazy. **A policy may declare `framework_version`** (F-65): equal or older is enforced, newer is refused. An unknown rule name in Rego is an undefined value rather than an error, so without this a policy authored for gates an older agent lacks is enforced minus those gates, silently — hcsshim denies the same case structurally. Absent is legacy and allowed; explicit-but-malformed is an error. **A container authorized by a fragment is now named by reference, not position** (F-67): policy state recorded the container's *index* into `base ++ fragment` containers, and that list is a comprehension over the fragments currently loaded — so delivering a fragment declared earlier in the list inserts entries and shifts every recorded index after it, re-binding a running container's rules to a different container at a moment the host chooses. State now stores `{feed, svn, idx}` (or `{base, idx}`), and resolution re-runs the declaration gates and pins the SVN exactly, so a container authorized under one fragment version is never evaluated against another's. **A fragment can now actually contribute a container** (F-69): the contract 
ules.rego documents keys a fragment's containers by its feed, and a feed is an OCI reference, so the only way to write that key is a quoted package path (`package agent_policy.fragments["<feed>"]`) — which the agent refused, making the whole contribution path unreachable while every delivery test stayed green. The agent now accepts exactly that form for the feed the SRM verified from the fragment's own COSE envelope, which is stricter than the shared package it sits beside: the namespace key is the signed identity, so one publisher cannot write another's.
