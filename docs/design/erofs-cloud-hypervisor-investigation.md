# EROFS with Cloud Hypervisor

## Current finding

Upstream Kata `runtime-rs` consolidates multi-layer EROFS images into one
virtual disk using a VMDK descriptor. Cloud Hypervisor added read-only flat
VMDK support in
[PR #8599](https://github.com/cloud-hypervisor/cloud-hypervisor/pull/8599).
The supported `monolithicFlat` and `twoGbMaxExtentFlat` formats include the
format generated by Kata.

VMDK is not required by EROFS itself. It is used to reduce many image-layer
files to one VM block device, avoiding excessive PCI devices and hotplug
operations.

Kata must preserve `BlockDeviceFormat::Vmdk` when converting a runtime-rs
block device into a Cloud Hypervisor `DiskConfig`. Sumedh Sharma implemented
this in `Sumynwa/kata-containers:sumsharma/enable_erofs_vmdk_for_clh`, commit
`5042445d3e`.

## Cloud Hypervisor MSHV regression

The VMDK implementation was tested with the Azure MSHV SEV-SNP flow using the
same Kata runtime, EROFS-enabled `6.1.58.mshv8` guest kernel, IGVM, guest disk,
and VM configuration.

- Microsoft `msft/v51.1.101` boots and runs a single-layer EROFS workload in
  approximately 11 seconds.
- Upstream v52.0 completes the same workload in approximately 17 seconds.
- Upstream v53.0 and the VMDK PR head take more than 90 seconds to reach
  `/sbin/init`.

A git bisect between v52.0 and v53.0 identified the first slow commit:

```text
4091e965b850133e90e674dadffed65ef287e975
vmm: return all-ones for unregistered MMIO reads
```

That commit changes missing MMIO reads from leaving the emulator buffer
unchanged, which is normally zero on this MSHV path, to returning `0xff`.

Both v52 and the slow build perform approximately 580 missing MMIO reads while
probing PCI and legacy devices. The first reads include local APIC addresses
`0xfee00020` and `0xfee00030`, not only PCI configuration space. The all-ones
build additionally accesses the suspicious address `0x7fffffee004` and then
spends roughly 90 seconds in early kernel initialization.

The slow boot is caused specifically by returning `0xff` for the missing LAPIC
ID read at `0xfee00020`; changing only the LAPIC version read does not help.
Before `4091e965`, the zero-initialized emulator buffer remained unchanged.

The working prototype:

- reverts `4091e965`, restoring the previous missing-MMIO behavior;
- applies AMD SME physical-address reduction only for the MSHV backend, leaving
  KVM behavior unchanged.

With these changes, single-layer BusyBox and eight-layer `nginx:alpine`
GPT+VMDK EROFS workloads both complete in approximately 11 seconds. The
KVM-only feature configuration also compiles successfully.

MSHV test coverage was also temporarily removed upstream in commit
`e4a6208a8` (`build: Temporarily drop the MSHV CI jobs`). Commit `47e88d26e`
decoupled the `igvm` and `sev_snp` features from implicitly enabling `mshv`;
MSHV builds must now explicitly use `--features mshv,sev_snp`.

## Recommended prototype path

Microsoft publishes newer MSHV-focused Cloud Hypervisor tags beyond the
validated `msft/v51.1.101`:

```text
msft/v51.1.110
msft/v51.1.116
msft/v52.0.92
msft/v52.0.95
msft/v52.0.107
```

`msft/v52.0.107`, dated July 16, 2026, was built with `sev_snp` and validated
with the same Kata runtime, IGVM, guest disk, and single-layer EROFS workload.
It completed in approximately 18 seconds. This demonstrates that the slow boot
is not a general regression in the maintained Microsoft MSHV line; it is
specific to upstream Cloud Hypervisor after commit `4091e965`.

The Azure Linux production repository currently packages
`cloud-hypervisor-51.1.101`; the newer Microsoft tags must be built from
source. None of the Microsoft v51 or v52 tags contains flat VMDK support.

The validated prototype uses the VMDK PR head `f50661ff` with
`cloud-hypervisor-mshv-vmdk-compat.patch`, plus the Kata `FlatVmdk` propagation
from commit `5042445d3e`.

Backporting VMDK to `msft/v52.0.107` remains an alternative, but the VMDK
commits depend on the newer `block/src/formats` refactor and do not cherry-pick
cleanly.

## Previous upstream approach

Upstream initially supported non-fsmerged multi-layer EROFS by attaching each
containerd layer as a separate raw block device. Kata-agent mounted every EROFS
device and combined the directories with OverlayFS.

[Kata PR #13085](https://github.com/kata-containers/kata-containers/pull/13085)
replaced this with GPT+VMDK. Its commit `0bd150e5f1` describes the earlier
implementation as the "one-device-per-layer approach" and identifies PCI slot
exhaustion for images with many layers as the reason for consolidation.

The old path was superseded rather than invalidated. Restoring it as a fallback
for hypervisors without VMDK support would reuse native containerd EROFS and the
existing kata-agent multi-layer handler.

## Microsoft prototype

The `erofs-main` and `mitchzhu/tardev-erofs-pr` branches avoid VMDK by retaining
the tardev transport:

1. Convert each OCI layer into a separately mountable EROFS image.
2. Hotplug every layer as a raw virtio-blk device.
3. Mount each EROFS device independently in the guest.
4. Combine the mounted directories with OverlayFS.

This works with Cloud Hypervisor but retains the custom tardev snapshotter and
scales the VM device count with the image layer count.

## Options

1. Retain tardev and change its layer format from tarfs to EROFS.
2. Use native containerd EROFS, but add a `runtime-rs` Cloud Hypervisor path
   that restores the previous upstream per-layer raw-device behavior.
3. Use upstream's VMDK design with a Cloud Hypervisor build that includes flat
   VMDK support and does not contain the MSHV missing-MMIO regression.

Option 3 is now preferred for the prototype. Option 2 remains a fallback if the
VMDK commits cannot be cleanly backported to a known-good MSHV base.
